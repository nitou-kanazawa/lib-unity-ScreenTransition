# split-commits

現在の作業内容を論理的な単位に分解し、個別にコミットするコマンド。

## 手順

### 1. 変更内容の収集

以下のコマンドを実行して、すべての変更を把握する：

```bash
git status
git diff
git diff --cached
```

### 2. 変更の分析と分解

収集した変更を以下の観点で論理単位に分解する：

- **機能単位**: 1つの機能や目的に関連するファイル群
- **変更種別**: feat / fix / refactor / docs / style / test / chore
- **依存関係**: 他の変更に依存する場合は、依存先を先にコミット

### 3. 分解案の提示

以下の形式で提案する：

```
📦 コミット分解案

1. <type>: <日本語の説明>
   - <ファイルパス>
   - <ファイルパス>

2. <type>: <日本語の説明>
   - <ファイルパス>

（分解不要な場合は単一のコミットを提案）
```

### 4. ユーザー確認

```
この内容でコミットしますか？ (yes/no/edit)
- yes: 提案通りにコミット実行
- no: キャンセル
- edit: 分解案を修正
```

### 5. コミット実行

`yes` の場合、以下の手順で1つずつコミットを実行：

```bash
# コミット1
git add <対象ファイル>
git commit -m "<type>: <メッセージ>"

# コミット2
git add <対象ファイル>
git commit -m "<type>: <メッセージ>"

# 以降繰り返し
```

各コミット完了後、進捗を報告する：
```
✅ 1/3 完了: feat: ユーザー認証機能の追加
✅ 2/3 完了: fix: null参照エラーの修正
✅ 3/3 完了: refactor: 不要なコメント削除

🎉 すべてのコミットが完了しました
```

## Conventional Commits タイプ一覧

| タイプ | 用途 |
|--------|------|
| feat | 新機能 |
| fix | バグ修正 |
| refactor | リファクタリング（機能変更なし） |
| docs | ドキュメントのみの変更 |
| style | コードの意味に影響しない変更（空白、フォーマット等） |
| test | テストの追加・修正 |
| chore | ビルドプロセスや補助ツールの変更 |
| perf | パフォーマンス改善 |

## 注意事項

- Untracked files は内容を確認してから適切なコミットに含める
- 1ファイルに複数の論理的変更がある場合は、`git add -p` で部分ステージングを検討
- コミットメッセージは日本語で簡潔に記述する
